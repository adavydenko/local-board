# Dogfood comparison: v0.0.1 → v0.0.2

This comparison uses the two blind, instrumented clean-room runs: [v0.0.1](v0.0.1-rerun.md) and [v0.0.2](v0.0.2-rerun.md). Both used the same three-part Focus Board scenario and fixed scoring rubric. The v0.0.2 evaluator froze its scores before reading the v0.0.1 result.

| Agent discovery/onboarding | 10% | 3.0 | 5.0 | +2.0 |

| Runtime operations | 5% | 3.0 | 3.0 | 0.0 |
| Traceability | 10% | 4.5 | 4.5 | 0.0 |
| **Weighted total** | **100%** | **3.35** | **4.30** | **+0.95** |

The normalized score improved by 0.95 points, or about 28% relative to the v0.0.1 score. Gains were concentrated in the release's intended areas: discovery, machine-readable bootstrap, credential lifecycle, and real multi-actor orchestration. Package installation, planning, lifecycle correctness, runtime process handling, and traceability were essentially unchanged.

## What clearly improved

1. **Fresh-agent discovery:** `init` now produces a root `AGENTS.md` bridge. The v0.0.2 evaluator discovered policy and skill without the v0.0.1 circular-discovery gap.
2. **Bootstrap automation:** JSON actor output removed human-string parsing. Installed instructions exposed the MCP URL, headers, and required Accept contract, avoiding the v0.0.1 HTTP 406 trial and error.
3. **Coordinator autonomy:** the admin created two implementation actors and a viewer entirely through MCP.
4. **Credential lifecycle:** rotation immediately invalidated the previous token while preserving the identity and enabling the replacement.
5. **Relevant tool discovery:** members and viewers received smaller catalogs, and viewer mutation was rejected server-side.
6. **Attribution:** issue activity was split across distinct authenticated implementers instead of one all-powerful coordinator.

## What did not improve enough

1. **Core interaction cost:** both runs used exactly 53 issue-addressed calls. The workflow remains verbose for a three-task mini-project.
2. **Runtime lifecycle:** Ctrl-C still prints a traceback and exits non-zero; no explicit readiness or stop mechanism exists.
3. **Credential logging safety:** tokens are easier to capture and rotate, but token-bearing MCP responses still create a client-side logging hazard. The v0.0.2 evaluator experienced and remediated an ignored-log near-miss.
4. **Permission granularity:** member hides credential administration but can still mutate broad project configuration. There are no project-, issue-, or capability-scoped tokens.
5. **Completion integrity:** acceptance criteria, checklist completion, reviewer rules, and branch patterns remain agent discipline rather than universal terminal-transition gates.
6. **Error ergonomics:** domain errors use HTTP 200 and require inspection of `result.isError` and `structuredContent.error`.

## Decision

v0.0.2 materially improves suitability for coordinator-led local multi-agent work and validates the release's main product hypothesis. It is now credible for controlled single-host orchestration where the coordinator owns a secret-aware MCP client.

It is not yet a low-ceremony or hardened distributed coordination service. The next highest-leverage work is clean process lifecycle/readiness, safer credential-response handling, narrower member capabilities, and reducing routine context/transition call amplification.
