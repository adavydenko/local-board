# Local Board v0.0.2

Local Board v0.0.2 focuses on autonomous agent onboarding and coordinator-led multi-agent work. A coordinator can now bootstrap with machine-readable credentials, provision least-privilege subagent identities through MCP, rotate compromised credentials, and expose a smaller role-appropriate tool catalog to each actor.

## Highlights

### Coordinator-managed subagent identities

Authenticated administrators can now manage subagent credentials without accessing SQLite:

- `create_actor` provisions an `agent` or `human` with the `member` or `viewer` role and returns its bearer token once;
- `rotate_actor_token` immediately invalidates the actor's previous token and returns a one-time replacement;
- provisioning and rotation are recorded in the immutable activity log;
- non-admin actors receive a structured `forbidden` error for credential-management calls.

Treat the `create_actor` and `rotate_actor_token` responses as secrets. Capture tokens directly into the orchestrator's secret store or worker environment; do not place them in prompts, issues, comments, logs, or tracked files.

### Machine-readable coordinator bootstrap

The CLI can emit actor credentials as JSON, avoiding fragile parsing of human-oriented output:

```bash
local-board init
local-board actor coordinator --kind agent --json
local-board serve
```

The first actor remains the bootstrap administrator. Subsequent implementation workers should normally be provisioned as `member`; audit-only workers should use `viewer`.

### Role-aware MCP discovery

`tools/list` is now filtered for the authenticated identity:

- administrators see the complete tool catalog;
- members do not see actor credential/role administration tools;
- viewers see only read and discovery tools.

Authorization is still checked for every invocation. The filtered catalog reduces irrelevant choices for subagents but is not the security boundary by itself.

### Discoverable, non-destructive agent onboarding

For a repository without root agent instructions, `local-board init` now creates an `AGENTS.md` bridge that points agents to `.local-board/AGENT.md` and the repository-local Local Board skill.

Existing root `AGENTS.md` files are never overwritten, including when Local Board-owned onboarding templates are refreshed. When an existing file does not reference `.local-board/AGENT.md`, `local-board doctor` reports an `agent_discovery` warning with the required manual action.

## Documentation and operational improvements

- Added a coordinator bootstrap and secure credential-handoff guide.
- Documented that claims are renewable leases with a 30-minute default rather than permanent locks.
- Clarified which issue operations use optimistic revisions and which related records have independent identifiers.
- Clarified that `available_transitions` does not prove acceptance criteria, checklist, reviewer, or branch-policy completion.
- Documented the single-host SQLite persistence boundary and behavior of fresh Git clones.
- Updated recovery documentation to match the implemented `backup` and guarded `restore --force` commands.
- Added a reproducible dogfood evaluation protocol and an instrumented v0.0.1 comparison baseline.

## Upgrade notes

1. Upgrade the package and restart the Local Board server so MCP schemas and authorization behavior are refreshed:

   ```bash
   python -m pip install --upgrade local-board==0.0.2
   local-board doctor --offline
   local-board serve
   ```

2. Run `local-board init` once in each repository. It keeps an existing project configuration and existing onboarding files, while adding missing artifacts such as the root discovery bridge.
3. If the repository already has an `AGENTS.md`, merge the Local Board bridge instructions manually; `doctor` warns until `.local-board/AGENT.md` is referenced.
4. Reconnect MCP clients or refresh `tools/list`. Clients that cached the v0.0.1 catalog may otherwise continue showing tools that are hidden for their role.
5. Give every concurrent subagent a separate actor token. Use `rotate_actor_token` after suspected disclosure or before reassigning a persistent identity.

No database schema migration is introduced by the coordinator credential-management changes. Existing actors and tokens continue to authenticate until an administrator rotates them.

## Compatibility notes

- `tools/list` output now depends on actor role. This is an intentional behavioral change for clients that compare or cache the full catalog.
- MCP actor provisioning intentionally cannot create another administrator. Promote an existing actor separately with the admin-only `set_actor_role` operation when necessary.
- Plaintext tokens are still returned exactly once. JSON output makes automation safer but does not make stdout or MCP response logging safe.
- Local Board remains a single-host, repository-local service; it does not synchronize operational SQLite state between machines.

## Validation

The release changes are covered by unit, integration, and end-to-end tests for:

- admin provisioning and token rotation;
- immediate invalidation of the previous token;
- authorization failures for non-admin actors;
- role-filtered MCP tool discovery;
- machine-readable `actor --json` output;
- root `AGENTS.md` creation and preservation of existing instructions;
- doctor detection of missing agent discovery instructions.

The expanded suite contains 62 tests, including a release-version consistency check. The v0.0.1 dogfood rerun remains the pre-release comparison baseline; v0.0.2 should be rerun through the same clean-room protocol after the package is published.

## Known limitations

- MCP client registration remains client-specific; `init` installs instructions and skill metadata but cannot modify every agent runtime's global MCP configuration.
- Acceptance criteria, checklist completion, reviewer requirements, and branch naming remain agent responsibilities rather than universal terminal-transition gates.
- Bearer tokens do not currently expire automatically and are not scoped to a single project or issue.
- The server is designed for a local foreground process and does not include a built-in service manager or multi-host database synchronization.

## Maintainer release checklist

Before publishing:

- set the package version to `0.0.2` in both `pyproject.toml` and `local_board/__init__.py`;
- run the complete test suite and build both wheel and source distribution;
- verify the wheel metadata reports `0.0.2`;
- verify MCP `serverInfo.version` reports the released version;
- create and publish the GitHub release with tag `v0.0.2` so Trusted Publishing can upload the artifacts to PyPI.
