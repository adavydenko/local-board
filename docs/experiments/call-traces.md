## Поправка к предыдущей оценке

В отчёте я написал «124 обращения там, где хватало ~28». Число 28 — это **измеренный**
результат эксперимента 3 (4 задачи плюс два ревью, ~7 обращений на задачу), а не
теоретический минимум. Минимум ниже, и он ближе к тому, что вы предположили.

### Честный пол для одной задачи

Без батчинга, с дефолтным workflow `todo → in_progress → in_review → done`
и включённым `require_assignee_before_start`:

| # | Вызов | Зачем он обязателен |
| --- | --- | --- |
| 1 | `list_issues` | выбрать задачу; возвращает `identifier`, `status`, `revision`, `priority`, `assignee_id` |
| 2 | `get_issue_context` | **описание задачи** — `list_issues` его не возвращает, а в нём лежит вся спецификация |
| 3 | `claim_issue` | атомарный захват, требует `expected_revision` |
| 4 | `transition_issue` → `in_progress` | политика не пускает в работу без заявки |
| 5 | `add_comment` | результат работы, контракт для следующего агента |
| 6 | `transition_issue` → `in_review` | лестница не даёт прыгнуть в терминал |
| 7 | `transition_issue` → `done` | закрытие |

**7 обращений.** С батчингом соседние по времени вызовы схлопываются:

| # | Батч | Вызовов внутри |
| --- | --- | --- |
| 1 | `list_issues` + `get_issue_context` | 2 |
| 2 | `claim_issue` + `transition_issue(in_progress)` | 2 |
| 3 | `add_comment` + `transition_issue(in_review)` + `transition_issue(done)` | 3 |

**3 обращения = 3 хода модели на задачу.** Это ровно ваша схема: посмотреть список,
взять и пометить себя, поработать, закрыть с комментарием.

Единственное, что мешает батчам 2 и 3 быть надёжными — обязательный `expected_revision`:
внутри массива нельзя подставить ревизию, вернувшуюся из предыдущего вызова, поэтому
её приходится угадывать как `+1`. При конфликте отваливается весь хвост батча.

Итого три числа: **пол — 3**, **дисциплинированный прогон — 7**, **импровизация — 31** на задачу.

## Что из этого вина инструкции, а что — API

**Инструкция (`local_board/templates/local-board-skill.md`)** прямо порождает:
преамбулу из четырёх вызовов («Start work», шаги 1–4), капельное закрытие чек-листа
(«Mark checklist items as work completes»), повторное полное чтение перед закрытием
(«Finish or hand off», шаг 1) и текущие комментарии. Она же ни разу не упоминает
`get_available_transitions` и не знает слова «батч».

**API** порождает: невозможность закрыть чек-лист иначе как по `item_id`; отсутствие
описания задачи в `list_issues` (из-за чего полное чтение обязательно); эхо всего
объекта в ответах мутаций; обязательный `expected_revision`, ломающий батчи;
`release_issue`, стирающий assignee вместе с лизом; отсутствие подписки, из-за
которого ожидание чужой работы вырождается в опрос.

**Модель** порождает: четыре дословных повтора. Но и они — следствие того, что
полезные три поля лежат внутри 30–60 килобайт.

## Как проверить самостоятельно

Сырой лог: `logs/mcp-calls.jsonl` в рабочей директории эксперимента, по строке на вызов:

```json
{"ts": 1755635, "actor": "agent-opus", "method": "tools/call",
 "tool": "get_issue_context", "req_bytes": 118, "resp_bytes": 52210,
 "status": 200, "ms": 12.4}
```

Воспроизвести таблицы можно так:

```bash
# трасса одного агента
python3 -c "
import json
rows=[json.loads(l) for l in open('mcp-calls.jsonl')]
a=sorted([r for r in rows if r['actor']=='agent-opus'], key=lambda r:r['ts'])
t0=a[0]['ts']
for n,r in enumerate(a,1):
    print(n, round(r['ts']-t0), r['tool'], r['resp_bytes'])
"

# дословные повторы подряд
python3 -c "
import json
rows=sorted([json.loads(l) for l in open('mcp-calls.jsonl')], key=lambda r:r['ts'])
for act in {r['actor'] for r in rows}:
    a=[r for r in rows if r['actor']==act]
    for i in range(1,len(a)):
        if a[i]['tool']==a[i-1]['tool'] and a[i]['resp_bytes']==a[i-1]['resp_bytes']>1000:
            print(act, a[i]['tool'], a[i]['resp_bytes'], round(a[i]['ts']-a[i-1]['ts']))
"
```

Инструментация — это обёртка вокруг MCP-клиента, дописывающая строку в лог на каждый
`tools/call`. Ничего специфичного для Local Board в ней нет; тот же приём применим
к любому MCP-серверу.
